# Known Pitfalls — DrumWave Personal Wallet Prototype

Recurring quirks found during the 2026-07-30 full-codebase audit (see `components.md` for the component/screen inventory this was gathered alongside). Each represents a pattern that already cost a correction round once — watch for it before repeating it in new screens.

- **Transparent `<button>` tap-target overlays are the dominant interactivity pattern.** Most screens render a single static, read-only Figma-exported image/component and stack absolutely-positioned invisible `<button>` elements on top at hardcoded pixel coordinates to make regions clickable (e.g. `AccountSettingsScreen`, `RequestDrumwaveDataScreen`, `UserProfileScreen`, `DataRequestConfirmScreen`). This is fragile: any change to the underlying Figma export's layout silently breaks the tap target without any visible error. When touching one of these screens, re-verify the overlay coordinates against the current export rather than assuming they still line up.

- **"Mask/override the read-only import" pattern recurs across otherwise-unrelated screens** — each screen invents its own fix rather than reusing a shared technique:
  - `MyCertificatesScreen` redraws a corrected badge over the import's own oversized one.
  - `OfferCampaignScreen` injects a scoped `<style>` tag to force font-weight on the import's CTA label without editing the protected import.
  - `OneDspHomeScreen` injects CSS to hide a bottom nav baked into the import in favor of the shared `OneDspBottomNav`.
  - `PhotoSavedScreen` paints a solid cover div over the import's static baked-in toast, then re-implements an animated version on top.
  - `PhotoSelectModalScreen` fully replaces the import's Save/Cancel buttons (documented bug: invisible black-on-black styling) with custom components.
  If you need to override part of a baked import, check here first for the closest precedent rather than inventing a fifth approach.

- **Some screens are hand-built from scratch instead of wrapping a Figma import**, specifically because the generated import broke the build or clipped content: `DataCertsLoadingScreen`, `RequestDataProgressScreen`, `OfferClaimingLoadingScreen`, `ReviewApplicationLoadingScreen`, `UploadDataScreen`. `DataCertsLoadingScreen`'s comment explicitly notes the generated import (~400KB+ of inline SVG paths) tripped Babel's compiler. If a new screen's Figma export is unusually large/complex, expect the same failure mode and budget for a hand-rebuild rather than debugging the generated file.

- **Several "shared" status bars and back arrows are reimplemented locally instead of importing `@/app/components/ui/StatusBar`.** `HowToGetDataScreen`, `OfferClaimingLoadingScreen` (as local `StatusBarPro`), `ReviewApplicationLoadingScreen` (as local `StatusBarPro`), `UploadDataScreen` (as a second local `StatusBar`), and `RequestDataProgressScreen` all rebuild the iOS status bar from raw SVG path data. Same for the back-arrow icon — the same path constant is hardcoded independently in `FaqScreen`, `LegalScreen`, `HowToGetDataScreen`, and again inside `HomeRequestDataBeforeDspScreen`. Reuse `StatusBar` and check `components.md`'s shared-chrome table before rebuilding either.

- **Hardcoded hex colors and font-family strings bypass the CSS variable tokens** in a meaningful minority of screens even though most of the codebase uses `var(--color-*)`/`var(--font-*)`. Notable offenders: `ConfirmApplicationScreen` (`#1d2023`, `#E3E3E3`, `#444BAC`, `#3642EB`), `ContactSupportScreen` (`#111`, `#2a2a2a`, `#666`), `HomeRequestDataBeforeDspScreen` (`#070707`, `#16BE76`, `#C82628`, hardcoded `'Titillium Web'`/`'Open Sans'` strings), `HowToGetDataScreen` (`#121212`, `#dd2222`, `#0091ff`). Prefer the design-token variables when touching these files; don't treat the existing hardcoded values as license to add more.

- **Dev Mode / Figma-export artifacts show up as real content, not just annotation overlays.** `DataCertsDetailScreen` has a stray "Home Indicator" element left ~1097px below the real content, only hidden by `overflow:hidden` — if that wrapper is ever changed, the artifact becomes visible. Several `@/imports/` folders also carry raw, un-renamed Figma layer names (`UnnamedComponent-1`, `Frame2095586464`, etc.) — expect these; they're cosmetic only and not a sign something is broken.

- **Known near-duplicate / inconsistent sibling screens** (full detail in `components.md`): `SmartPlanDetailScreen`/`Smart2PlanDetailScreen` are true duplicates of the same Figma export; `TermsConditionsScreen`/`SmartTermsConditionsScreen` and `SuccessfullyJoinedScreen`/`SmartSuccessfullyJoinedScreen` differ not just in branding but in which nav callbacks are actually wired (the "Smart" variants are missing functionality the base screens have). Don't assume a "Smart"-prefixed screen is functionally equivalent to its base counterpart — check its actual props before reusing a pattern from one on the other.

- **A few components were clearly built for reuse and then bypassed.** `DataContributionStep`, `GoalStep`, `RedRingField`, `RingField`, and `ui/StatsRow` all exist fully built but are never imported anywhere — in two cases (`DataContributionStep`, `GoalStep`) the consuming screen has a comment admitting its logic was "lifted"/"mirrors" the component instead of importing it. Before rebuilding similar functionality, check whether one of these orphaned components already does it — reuse it directly rather than re-deriving a third implementation.

- **Figma's colon-suffixed font names are invalid CSS and silently fall back (FIXED 2026-07-30 via a CSS shim — read this before editing fonts).** The raw exports style text as `font-['Titillium_Web:SemiBold',sans-serif]`, which compiles to `font-family: "Titillium Web:SemiBold", sans-serif`. That is Figma's internal "family:style" notation, not a real CSS family — the `@font-face` rules from Google Fonts register plain `'Titillium Web'` with a numeric `font-weight`. The colon-suffixed name matches nothing, so the browser skips it and renders the generic `sans-serif` (OS default UI font) instead of Titillium Web. Verified live via `getComputedStyle` on `ApprovedNotJoinedScreen` (`@/imports/Home/index.tsx`), where ~90% of text nodes are affected. Figma Make never shows this because its canvas resolves fonts through an internal font DB, not real CSS matching. Scope was 3,078 occurrences across 168 files. **Fixed by a shim at the bottom of `src/styles/globals.css`** that matches the literal class string (`[class*="Titillium_Web:SemiBold"]`) and supplies the right family + weight — not by editing `src/imports/`, since those are regenerated on every Figma re-export and ~40% of screens are still to come. The shim is unlayered so it beats Tailwind's layered utilities without `!important`. **New screens are corrected automatically; do not "clean up" the shim.**
  Weight handling deliberately differs by family, because the exports differ: Titillium rows carry no Tailwind weight class (1 of 1206 does) so the shim sets the weight, while Open Sans / SF Pro rows already carry a correct one (`font-normal`, `font-bold`, `font-[590]`) so the shim only corrects the family.

- **`SemiBold` is 600, NOT the design system's `font/weight/semibold: 500`.** The Figma variable says 500, but Titillium Web has no 500 face (its axis is 200/300/400/600/700) — requesting 500 silently degrades to 400/Regular. Verified in-browser by width probe: weight 500 and weight 400 render identically. The style name (`SemiBold`) is the reliable signal; the numeric variable is not. Corroborated by `guidelines/components.md` ("Titillium Web 600") and the pre-existing `button { font-weight: 600 }` rule. **Per the project rule that the screen takes priority over the design system, trust the style name.** Worth correcting `font/weight/semibold` to 600 in the Figma variables so the two stop disagreeing.

- **`fonts.css` must load every weight the exports reference.** It previously requested `Open Sans:wght@400;600` only, leaving `Open_Sans:Bold` (172 uses), `:Light` (5) and `:Italic` (4) with no face to resolve to even once the family name was correct. Now loads Titillium 200/300/400/600/700 and Open Sans 300/400/500/600/700 + italic 400. Adding a new text style in Figma means checking this list.

- **Three foreign typefaces leaked in from Figma defaults (Inter/Roboto FIXED AT SOURCE 2026-07-30; SF Pro intentional).** `Inter` is Figma's default font for a text layer created without applying a style; `Roboto` is the Android/Google default; `SF Pro` is the iOS status-bar chrome and is *correct* — the shim maps it to the `-apple-system` stack, leave it.
  The giveaway for Inter: in the airline list, United/American/Alaska/Greyhound were all `Titillium_Web:SemiBold` and only **"Spirit"** was `Inter:Medium` — one row of five, i.e. a mistake, not a design decision.
  **Fixed in the Figma file** (`hKioJ4kuKEe4VnFdJHPeZt`, "Page 1"): all **325** stray text nodes retyped to Titillium Web — far more than the 43 visible in the exported code, since the export only covers built screens. Concentrated in *PdW Account Profile* (198), *Requests page* (46), *Home* (26). Mapping used: Inter Regular→Regular, Inter Medium→**SemiBold** (Titillium has no Medium face, and "Spirit" belongs with its SemiBold siblings), Inter Semi Bold→SemiBold, Inter Bold→Bold, Roboto Regular→Regular. Verified: 0 stray nodes remain; page is now Titillium Web (4589) + Open Sans (3370) + SF Pro chrome only.
  Caveat: 43 of those sit inside **remote library components** (`Categories`, `_Base / Tag` — `remote: true`, defined in a *different* Figma file). They were fixed with instance-level overrides here, so **the upstream library still has Inter**. Fix it there too, or new instances will reintroduce it and these overrides will mask future library updates.
  The CSS shim's Inter/Roboto rules are now belt-and-braces for already-exported screens; keep them until every screen is re-exported.

- **Andale Mono text is designer annotation — never restyle or render it.** Six monospace nodes ("To Eng: there was a text change in the…", "Rules for this page (from email):", "In app: Offers dissappear") sit on the canvas in *Account Creation* and *Offer 1.0*. They are notes to engineering, not UI, and must not be exported into any screen — see the Dev Mode artifact rule in the verification checklist.

- **Font fallback chains must stay sans-serif (FIXED 2026-07-30).** `--font-family-primary` in `src/styles/globals.css` was `'Titillium Web', Georgia, serif`. Whenever the Google Fonts webfont was slow, blocked (ad-blocker, corporate proxy), or offline, every heading/button consuming the token rendered in **Georgia** — a serif face installed on macOS, so it resolved to real Georgia rather than falling through. Now `'Titillium Web', sans-serif`, matching the existing `--font-family-secondary` pattern. Verified by width-measurement under a simulated font-unavailable condition (old chain → 332.13px/Georgia; new chain → 340.20px, exact match to the generic sans reference). Keep any future font token's fallback sans-serif — both project typefaces are sans.

- **`DaHomeScreen` is dead code** — not reachable from any `step===` case in `App.tsx`, fully superseded by `DaHomeFullWidthOverview1Screen`. Don't use it as a reference for "the current Da Home screen"; use the `-1` variant instead.
